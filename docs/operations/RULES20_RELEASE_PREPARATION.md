## Later production decision sequence

1. Recheck certified backend and frontend executable identities, paid state,
   source binding, admitted and retired frontiers, pending queue, reservations,
   last publication, cycles, freezing thresholds, and recovery headroom.
   Rehash every retained executable and its inventory independently. Confirm
   no concurrent maintenance. Verify that the Rules20 frontend actually
   accepts the installed Rules19 identity and direct-root certificate before
   any same-ID frontend upgrade.
2. With separate production authorization, install the compatible Rules20
   frontend first on `s2jxj-liaaa-aaaas-amynq-cai`, preserving the permanent
   origin. Verify certified executable, complete assets, routes, CSP,
   authenticated gameplay and Internet Identity binding. Keep the exact
   manufacturing frontend available for frontend-only recovery while the
   backend remains Rules19.
3. Select the backend path from the *fresh* journal and source condition.
   A healthy drained Rules19 predecessor takes the ordinary authenticated
   Rules20 transition. An obstructed predecessor with the specifically
   supported digit-leading authorization failure uses the dedicated
   controller-authorized Rules19 recovery checkpoint, preserves its ordered
   admitted prefix and historical policy, retires it, then takes the ordinary
   Rules20 transition. Do not try ordinary preparation against an undrained
   obstructed journal. Neither path resets the world or rewinds source.
4. After the first durable recovery or Rules20 commitment, retain the exact
   successor backend executable as the compatible same-ID recovery module.
   The old Rules19 executable must not be reinstalled across that boundary.
   Retain the Rules20 frontend candidate as the frontend recovery module once
   the backend identity requires it. Confirm publication, receipts, source
   health and independent replay after each boundary.
