# Resumable kernel contract and Life conformance slice

The pure Rust `ResumableKernel` owns only `step(work_units) -> Pending|Complete`. A work unit is not game time. The JavaScript generic runner has no Life/B2Z import; it accepts a kernel factory, verifies initial-state/input commitments, optionally roundtrips a cursor at each safe point, and creates a manifest only after completion.

Kernel authors must interpret the sealed logical context, use canonical ordering/arithmetic, and emit final canonical state/events/accounting independent of work partition. The host cannot infer game-specific time correctness from opaque bytes. A future canister host persists staged state instead of exposing incomplete work. The offline runner's slice limit aborts without a manifest; it is a safety bound, not a gameplay rule.

## Life rules for conformance only

Finite rectangular board with dead cells beyond its edges. Eight-neighbour Life: a live cell survives with two or three live neighbours; a dead cell is born with three. Survivors retain their owner. Birth color is majority among the three parents; a three-way tie uses the lowest owner ID. Zero is dead; owner IDs are u16. These are deterministic test rules, not a finished game economy or fairness policy.

Limits: width/height 1–64, at most 1024 cells, 1–32 generations per segment. They bound the demonstration, not B2Z production capacity. Logical generation is u64; overflow rejects before simulation. One work unit evaluates one cell in row-major order against the unchanged current generation. Scratch state becomes current only when that generation is complete.

Events record changed cells in `(new_generation, row-major cell)` order. Scoring counts each owner's live cells over the **old** generation for each elapsed generation. Scores are per segment; financial entitlements and daily aggregation are not implemented.

## Codecs

All fields big-endian:

```text
Board:
  "LIFE0001", width:u16, height:u16, generation:u64, cells:[u16; width*height]
Events:
  "LIFEEVT1", count:u32, [generation:u64, cell:u32, before:u16, after:u16]*
Scores:
  "LIFESCR1", count:u32, [owner:u16, occupied_generations:u64]*
Cursor:
  "LIFECUR1", state_length:u32, Board,
  total_generations:u8, remaining_generations:u8, start_generation:u64, next_cell:u32,
  scratch:[u16; width*height], event_length:u32, Events, score_length:u32, Scores
```

Score entries strictly increase by owner; event entries strictly increase by generation/cell. Readers enforce versions, lengths, bounds, scratch invariants, generation consistency and no trailing data. A snapshot's digest must be authenticated by its holder/certified record before external bytes are used. A digest supplied alongside an untrusted snapshot is not a trust anchor. The Rust reader requires the host to do this; the JavaScript restore method takes an expected hash explicitly.

## Actual evidence versus future work

Python reference generation uses scatter-neighbour counting, while JS/Rust kernels gather neighbouring cells; the retained vectors are not generated by the implementation under test. JS tests compare bytes and hashes and serialize/restore at safe points, including every cell in the mixed scenario. Native Rust tests read the same TSV fixtures, but have not run here. Native/Wasm agreement is still a blocked gate.

This deliberately includes a useful part of S02 within the larger S01 package. It does not complete stable publication, authenticated snapshot distribution, migrations, full input application, the browser SDK, or the IC arena. B2Z currently contributes its independent memo module, not a playable second kernel. Do not claim that all games have been proven to fit merely because the interface is generic.
