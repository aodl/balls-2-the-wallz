# Documentation discipline and checkpoint delivery

## One normative location per rule

Keep protocol truth in versioned `docs/specs/` plus canonical fixtures. Design narrative belongs in architecture notes and ADRs; user rules are generated or reviewed against the same source. Historical documents remain clearly versioned. An implementation cannot silently reinterpret an old rules hash after a code refactor.

Each protocol change states its rationale, affected rule/config/schema versions, migration implications, test IDs, compatibility and activation boundary. Prefer a short ADR when choosing a meaningful alternative over duplicating long prose in many READMEs.

Required documentation at the relevant stage:

| Document | Purpose |
|---|---|
| Root README / current STATUS | What exists now, how to verify it, what is blocked |
| Architecture and authority map | Why each module/canister exists and what it may change |
| DTR input/seal/codec specification | Reproducible protocol rather than illustrative pseudocode |
| BTZ player rules | Prices, nonrefund conditions, capacity races, identity, scoring, spawn and extinction |
| Stable memory and migration registry | Memory IDs, schemas, durable operation states and retained history |
| Configuration manifest | Complete effective rules/economics/source/control identities and activation history |
| Testing matrix | Requirements mapped to executable tests and recorded outcomes |
| Operations runbooks | Install, upgrade, pause/recover, funding, payout reconciliation and evidence collection |
| Threat model / dependency policy | Trust boundaries, resource abuse and justified exceptions |
| IC reference register | Primary specifications/skills, reviewed dates, pinned versions/commits when adopted |
| Checkpoint report | Changed files, decisions, evidence, limitations and next gate |

Use structured deployment/config manifests and small semantic validators. Do not make correctness depend on exact README wording or a giant regex script. Documentation links and referenced schema/test identifiers should be machine-checked.

## Agent workflow

`AGENTS.md` records commands, architecture constraints, unsafe actions and evidence rules. Each new checkpoint begins by reading the prior checkpoint manifest, current specifications and failing/blocked gates. It must not reconstruct the state solely from conversational memory.

Research current official docs and relevant skills before changing external APIs. Capture the exact reviewed references, then pin actual implementations and toolchains. Do not auto-update skill contents, CLI versions or lockfiles during a reproducibility run. Example snippets may use different dependency versions or make assumptions incompatible with wallet-driven gameplay; reconcile them with the selected interfaces and tests.

## Checkpoint status model

Every checkpoint reports three separate things:

1. **Implementation scope:** planned / partially implemented / implemented for this stage.
2. **Verification:** gate-by-gate results with actual evidence, not a single optimistic percentage.
3. **Release eligibility:** denied / restricted test-only / eligible for the specifically authorized release.

A source checkpoint with blocked external checks remains useful. It cannot be relabeled release-ready. Critical external gates remain queued explicitly at the next runnable environment rather than disappearing from the narrative.

## ZIP contract

Each stage produces a complete source checkpoint with a stable root directory, not merely a patch requiring an unavailable earlier conversation. Include:

```text
README.md
STATUS.md
AGENTS.md
CHANGELOG.md
CHECKPOINT.json
FILES.sha256
source and actual lockfiles, once generated by real package managers
specifications, ADRs and test fixtures
verification report + logs + toolchain/capability information
runbooks and expected next commands
```

For build stages also include or identify canonical Candid, raw Wasm, uploaded package, source/rules/config/schema identities, SBOM and build evidence. When binaries cannot be built, omit them and record the block. Never include a placeholder binary or invented artifact hash as a real build.

Exclude credentials, local identities, private keys, secret environment files, `node_modules`, transient caches and compiler output directories unless selected release artifacts are explicitly intended. Retain upstream licenses/notices for copied dependencies/components. Do not silently assign a license to the user's new work.

Record predecessor checkpoint ID and archive hash, changed scope and unclosed decisions. Do not require Git to build an extracted ZIP: preserve explicit source revision/archive identity and a deterministic source-date value. Use sorted packaging entries and deterministic metadata when claiming reproducibility.

`FILES.sha256` covers all payload files except itself; verify exact coverage, not only listed checksums. Produce the ZIP hash as an external sidecar because a ZIP cannot contain a stable hash of itself. These hashes are integrity identities, not signatures. Later signed releases should identify the signing/control policy separately.

## Checkpoint integrity commands

This S00 includes a standalone verifier and unit tests. It checks safe relative paths, duplicates, extra/missing payload files and SHA-256 digests. The checker is intentionally dependency-free so it works without Rust/IC tools. It does not validate semantics, replace a security scanner or prove the future code is correct.

Future `xtask checkpoint` may orchestrate the same contract alongside build/tests. Re-run and preserve evidence after each meaningful code change; a predecessor's green report is not automatically inherited by modified source.
